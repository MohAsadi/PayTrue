## Versioning policy

Status: PROPOSED (part of the freeze fingerprint: an approval of the types is an approval of this policy).

* V1 The domain version string identifies the whole message set of a domain (`FastPay Mandates`, `FastPay Quote`). Any change to a type string, to a domain name, to the snapshot encoding or to a tag that a signature covers is a new domain version, deployed as new contracts; the previous contracts, and every signature made for them, are unchanged and cannot be replayed on the new domain because the domain separator differs.
* V2 A deployed contract supports exactly one domain version and one type string per message: there is no version negotiation, no fallback and no upgrade of a type string in place.
* V3 A type that is used inside a Permit2 witness is never edited: a changed `PayOnceIntent` is a new type with a new name (`PayOnceIntentV2`) under a new router address, so a signature for one can never validate on the other (09 section 5).
* V4 The snapshot encoding is versioned by its tag (`fastpay.migration.snapshot.v1`); changing a word, its order or its source is `.v2` and is a domain version change under V1, because `termsSnapshotHash` is signed.
* V5 The price-bounds registry is append-only: a published (token, currency, boundsVersion) entry is never changed or removed, so a mandate that pins a version always reads the band that its customer was shown. A new band is a new version.
* V6 Every change under V1 to V5 goes through the Freeze Change Request of 14 section 7 and re-derives the freeze fingerprint; an approval names the fingerprint it approves.
